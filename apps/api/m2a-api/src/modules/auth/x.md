# Architecture Review — Full Domain Model
Date: 27/05/2026
Participants: Matheus (Tech Lead), Brenno (Backend Dev), Ana (Frontend Dev)

Matheus opened the session by stating that the goal was to finalize the complete domain model for the M2A platform before starting the implementation of the diagram and transcript modules. He asked Brenno to walk through each entity and its responsibilities, and Ana to flag anything that would affect how the frontend consumes the data.

Brenno started with the User class. He explained that User is the central entity of the system and every other entity is owned by a user. The User class must have the following attributes: id of type string, name of type string, email of type string, password of type string, createdAt of type Date, and updatedAt of type Date. In terms of methods, User should expose updateProfile which receives name of type string and email of type string and returns void, changePassword which receives currentPassword of type string and newPassword of type string and returns a boolean indicating whether the operation succeeded, deleteAccount which returns void, and a static method called findByEmail which receives email of type string and returns a User or null.

Ana asked whether the password field would ever be returned to the frontend. Brenno confirmed it would never be exposed and that a sanitize method would strip it before any response left the backend. Matheus agreed and asked Brenno to add sanitize as a method on the User class that returns a UserPublic type, which is User without the password field.

Brenno then moved to the Transcript class. He described it as the entity responsible for holding everything related to an uploaded file. The attributes are: id of type string, userId of type string as a foreign key to User, filename of type string representing the original name of the uploaded file, fileType of type string which can be pdf or md, rawText of type string containing the full extracted content, sizeInBytes of type number, createdAt of type Date. The methods on Transcript are: extractText which receives a buffer of type Buffer and a fileType of type string and returns a string, validate which checks whether the file is within the allowed size and type constraints and returns a boolean, and getOwner which returns the userId string.

Ana noted that the frontend would need to display the filename and the upload date on the listing screen. Brenno confirmed both fields are present. Matheus added that fileType should be stored as a lowercase string to avoid inconsistencies when filtering on the frontend.

The next entity discussed was the Diagram class, which Brenno described as the core output artifact of the platform. The attributes are: id of type string, userId of type string, transcriptId of type string as a foreign key to Transcript, title of type string which is auto-generated from the filename initially, type of type string which can be sequence, c4, or class, mermaidCode of type string containing the raw Mermaid diagram output, status of type string which can be pending, processing, completed, or failed, processingTimeMs of type number representing how long the generation took, createdAt of type Date, and updatedAt of type Date. The methods on Diagram are: updateTitle which receives newTitle of type string and returns void, updateStatus which receives a status of type string and returns void, regenerate which receives diagramType of type string and returns a string, isCompleted which returns a boolean, and isFailed which returns a boolean.

Ana asked about the status field and whether the frontend should poll for updates. Matheus confirmed that for the MVP the generation is synchronous, so the status would always arrive as completed in the response. However the field should exist in the model so that migrating to async processing later requires no schema changes. Brenno agreed.

Brenno then introduced a new entity that had not been discussed before: the AgentExecution class. He explained that every time the system calls the Gemini API through the ADK, it should log that execution for observability and debugging purposes. The attributes are: id of type string, diagramId of type string as a foreign key to Diagram, agentName of type string representing which agent ran, inputText of type string containing what was sent to the agent, outputText of type string containing what the agent returned, tokensUsed of type number, durationMs of type number, success of type boolean, errorMessage of type string which can be null if the execution succeeded, and createdAt of type Date. The methods are: markAsSuccess which receives outputText of type string, tokensUsed of type number, and durationMs of type number and returns void, and markAsFailure which receives errorMessage of type string and returns void.

Matheus said this was an excellent addition and would make it much easier to debug prompt issues in production. Ana agreed it would also be useful to eventually show users a breakdown of how their diagram was generated.

The final entity discussed was the ApiKey class, which Matheus introduced as a future-facing entity for when the platform offers a public API. The attributes are: id of type string, userId of type string, keyHash of type string containing the hashed version of the API key, label of type string which is a human-readable name the user gives the key, lastUsedAt of type Date which can be null, expiresAt of type Date which can be null, isActive of type boolean, and createdAt of type Date. The methods are: revoke which sets isActive to false and returns void, isExpired which compares expiresAt with the current date and returns a boolean, and a static method generate which creates a new raw key, hashes it, and returns both the raw key for display and the ApiKey instance for storage.

Matheus noted that the raw key should only ever be shown once at creation time and never stored, following the same pattern used by GitHub and Supabase. Brenno confirmed he understood and would implement it that way.

Regarding relationships, the team agreed on the following: User has a one-to-many relationship with Transcript, User has a one-to-many relationship with Diagram, User has a one-to-many relationship with ApiKey, Transcript has a one-to-many relationship with Diagram since a single transcript could theoretically generate multiple diagram types, Diagram has a one-to-many relationship with AgentExecution since generating one diagram may involve multiple agent calls such as the analyzer and the generator running sequentially.

Brenno summarized the decisions made during the meeting: passwords are never returned in responses, fileType is always stored lowercase, Diagram status field exists from day one even though the MVP is synchronous, AgentExecution is logged for every Gemini call, and ApiKey raw values are shown only once and never persisted.

Matheus closed the session by assigning implementation ownership. Brenno will implement Transcript, Diagram, and AgentExecution. Matheus will implement ApiKey when the public API milestone begins. The User class is already partially implemented and Brenno will add the missing methods in the next sprint.
